Executive assessment

DeepWiki is useful and generally accurate as a compact orientation to the original Sonuvi enhancement layer: moOde/MPD remains a foundational playback domain, the API and static web host form the application tier, the display router is a deliberate stability boundary, and the legacy control surface is protected by a Track Key.

Its coverage is not a current architectural review of the repository, however. The overview navigation does not expose the complete numbered hierarchy. A recursive traversal of every same-repository DeepWiki link found and fetched 79 URL variants; after normalizing duplicate aliases and two non-page trailing artifacts, it covered 77 canonical numbered pages across sections 1–11. Every canonical page reported the same publication timestamp and source revision recorded above. No same-repository DeepWiki page linked by the traversed hierarchy was left unvisited.

3. DeepWiki claim classification

VERIFIED claims

The following claims are supported by the current source and documentation, with the scope qualifications noted below:

  1. **The application has a moOde/MPD foundation, an app-host API/web tier,

and browser/display surfaces.** The current root architecture.md and architecture.md describe this same split.

  1. The API and static web service are normally separate listeners. The

documented defaults remain API port 3101 and static UI port 8101. The stable display router is intentionally served from the UI surface rather than being tied to a fragile display implementation.

  1. The public state routes are central integration surfaces. The

/now-playing and /next-up family remains important to displays, controllers, and integrations, although current source-specific state is richer than the DeepWiki description implies.

  1. **Track Key protection remains real for the classic/server control

surface.** DeepWiki correctly identifies a bearer-like Track Key boundary for legacy control and configuration routes. This is not the only authentication domain in the current system.

  1. **moOde/MPD integration uses the host's existing player state and tools

rather than replacing moOde.** The current implementation still uses MPD and moOde-specific integration paths for MPD playback, queue, metadata, and hardware-facing behavior.

  1. The display layer has explicit modes and a builder-first Peppy path.

The current display and Peppy documentation supports the DeepWiki description of a stable display entry point, mode selection, and generated renderer state.

  1. **The UI commonly observes normalized server state rather than directly

coupling every surface to MPD.** This remains a useful design principle, but the normalized state now also has Qobuz, UPnP, radio, AirPlay, and device/mobile qualifications.

PARTIALLY CORRECT claims

  1. “MPD is the audio authority.”

This is correct for the MPD playback domain. It is not a universal authority statement for the Server. Current playback authority is source- and target-dependent:

- MPD/moOde owns the Home/local/radio paths that use MPD. - Qobuz Connect is observed and controlled through the enhanced PiBuZ receiver, with a separate remote queue and playback state. - UPnP has a Sonuvi control-point/renderer session and logical queue boundary; it is not just an MPD stream label. - native iOS playback has device-local state and uses Server contracts for shared observation/history during the transition.

The current playback-authority-by-mode.md already has the right direction but needs Qobuz and current UPnP sections.

  1. “The API is a stable router over moOde/library state.”

The API is still a stable control-plane boundary, but it now owns or mediates more than moOde/library state: mobile bearer sessions, Qobuz/PiBuZ observation and control, UPnP discovery and renderer sessions, audio diagnostics, history events, metadata enrichment, and external hardware integrations.

  1. “Track Key is the primary authorization model.”

Track Key remains primary for the classic web/controller routes. Native mobile routes use signed bearer sessions and scoped media/radio tickets. Mobile routes must not be described as raw Track-Key or raw MPD access. The current mobile-auth.mjs and api-endpoint-catalog.md establish the split.

  1. “UPnP is a stream-like playback mode.”

That shorthand appears in the older overview material, while DeepWiki page 7.9 provides a much more accurate control-point, renderer-session, mobile-bridge, and logical-queue description. The 7.9 treatment is a valuable architectural insight. Current main still extends it with the newer readiness polling, stale-observation protection, and duplicate-Play handling, so the page remains revision-stale rather than being absent or fundamentally wrong.

  1. **“Installation is represented by the installer and systemd/PM2

configuration described by DeepWiki.”**

The installer concepts are still useful. The live operational model also includes the Pi5 deployment helper, the installed systemd service, path-specific restart behavior, host-key pinning, and post-deployment verification. DeepWiki's excerpt did not establish the actual unit contents or the current Pi5 recovery procedure.

  1. “The API and web host are the main application boundary.”

This remains true, but source-specific remote systems and native mobile clients introduce explicit ownership boundaries inside that application boundary. A single “Server controls the player” statement is too broad.

OUTDATED descriptions or implications

  1. The analyzed revision is outdated. DeepWiki's source references stop at

dee06724. Current main adds the Qobuz, mobile, and current UPnP changes listed in the baseline.

  1. The implied UPnP capability is outdated. Current UPnP is a guarded

control-point and renderer-session subsystem, not merely a stream-like display mode.

  1. The apparent completeness of the route inventory is outdated. Pages

9.2, 9.6, and 9.7 cover important API and diagnostics families, but they predate the current main route set. Current Server additions include the expanded Qobuz controls/release lifecycle, mobile UPnP mutations, local-source, playback-event, history, and revision-specific audio-info behavior.

  1. The deployment description is operationally incomplete. It does not

describe the current primary Pi5 deployment helper, live service restart rules, or the verification requirements used for current backend changes.

  1. The documentation corpus itself has moved. The repository's canonical

editable knowledge base is docs/wiki-source/, with focused source-backed pages and runbooks. DeepWiki should not be treated as a second maintained documentation hierarchy.

INCORRECT when interpreted as a current complete architecture

No isolated sentence in the reviewed DeepWiki pages was proven flatly false against current source when read as a description of the original moOde-centered foundation. The following interpretation would be incorrect:

Sonuvi Server is only an MPD/moOde enhancement layer with one queue, one control authority, one Track-Key authorization model, and no independent Qobuz, UPnP, mobile, or native-device ownership boundaries.

That is not the current architecture. The safer classification for individual DeepWiki statements is PARTIALLY CORRECT, with the completeness implication classified as INCORRECT.

UNVERIFIED claims

The following could not be established from the available DeepWiki material and were not asserted as current facts:

  • exact contents, ordering, dependencies, and failure behavior of every

systemd unit

  • exact PM2 ecosystem behavior in the current deployment
  • whether every installer option still matches the live Pi5 installation
  • current runtime behavior of the live service, because this audit did not

restart services, deploy, or perform live playback tests

  • current Qobuz account/library behavior beyond the repository contracts
  • runtime behavior of external hardware that is separately maintained

These require source inspection, deployment inspection, or a deliberately authorized runtime test; they should not be inferred from DeepWiki.

4. Current architectural relationships DeepWiki does not fully capture

4.1 Multiple playback authorities and targets

The current system is better represented as a set of source/target domains than as a single player:

DomainState/control ownerQueue or identity boundaryServer role
Home/local/radio through moOdemoOde/MPDMPD queue and MPD/file-derived identityControl, normalization, queue shaping, history observation
Qobuz ConnectEnhanced PiBuZ receiver for remote playbackRemote Qobuz queue/occurrence and PiBuZ observationObserve, expose status/queue, issue guarded controls, perform explicit handoff/release
UPnP/OpenHome rendererSonuvi UPnP control point plus selected rendererProcess/session-owned logical queue and renderer transportDiscover, select, preflight, control, serialize startup, expose sanitized state
Native iOS playbackiOS deviceDevice-owned native queue/cache/catalog directionCurrent contracts, metadata/identity bridge, playback-event/history ingestion
AirPlay and other external pathsExternal receiver/targetSource-specific external transportObserve and normalize where supported; do not assume MPD ownership

The important distinction is between who currently plays bytes, who owns the queue, who owns identity, and who reports shared history. Those are not always the same component.

4.2 Multiple queues

The current documentation distinguishes playback from queue shaping, but it needs a single cross-system matrix. At minimum, the Server now has:

  • the moOde/MPD live queue
  • the Qobuz remote queue, including occurrence-preserving jump/control
  • the UPnP logical queue and renderer session
  • native iOS Home/device queues
  • saved Qobuz queues, which are durable remote captures rather than the live

MPD queue

Queue position, upcoming items, duplicates, persistence, and control commands therefore require source-specific semantics. A generic “Next Up is the queue” explanation is unsafe.

4.3 Multiple authentication domains

The current authorization boundaries are not interchangeable:

  • Track Key for classic/server control and configuration
  • signed mobile bearer sessions with scopes and expiry
  • short-lived mobile media/radio tickets where required
  • provider/receiver credentials and internal PiBuZ access
  • network and renderer trust boundaries for UPnP

The mobile boundary deliberately avoids exposing raw Track Keys, MPD paths, filesystem paths, or provider credentials to the native app.

4.4 Multiple identity systems

Track Keys, MPD file identity, Qobuz/PiBuZ identifiers, UPnP object/resource references, and mobile opaque IDs are not interchangeable. The history pipeline must qualify and deduplicate at the appropriate boundary instead of assuming that a displayed title or artwork URL is a canonical identity.

4.5 Shared history and scrobbling

The current history design is a server-side event pipeline:

  1. source-specific observation or an explicit mobile playback event enters the

Server

  1. the Server resolves/validates identity and source attribution
  2. qualification and deduplication are applied
  3. local history is recorded
  4. Last.fm submission is performed asynchronously when eligible

The MPD poller remains important, but it is not the only possible event source. Qobuz and Sonuvi-owned UPnP playback require suppression or qualification rules so that MPD observations do not create duplicate history. Native iOS reports through POST /v1/mobile/playback/events; it does not submit directly to Last.fm.

The existing centralized-playback-history-and-scrobbling.md documents most of this well, but its current-mode wording and review date need reconciliation.

4.6 Audio diagnostics distinguish facts from configuration

The current Audio Info contract separates:

  • source-reported format
  • decoded PCM
  • configured output
  • hardware-measured output
  • processing and volume configuration
  • conversion uncertainty
  • freshness and diagnostic provenance

Configured moOde output is not proof of measured DAC output. A stopped MPD stream is not proof that a Qobuz or external stream has no open hardware path. DeepWiki page 9.7 covers the underlying moOde, ALSA, and source-probe distinction, while the current diagnostics-interface.md and mobile contract add the repository-specific sanitization, freshness, and measured/configured semantics that still require reconciliation.

4.7 Metadata enrichment is provider-neutral

The current About architecture presents provider-neutral metadata to clients, with optional Apple Music editorial enrichment and bounded caching. Playback must not depend on an About lookup. DeepWiki covers portions of this through the Media Library, Metadata Inspector, iTunes/Motion Art, and page-6.6 About material, but page 6.6 is mislabeled as listening history and the current provider-neutral contract is clearer in about-metadata.md and apple-about-metadata.md.

5. Newer subsystem findings

Qobuz Connect

Current source and documentation establish a working Server/PiBuZ bridge with separate observation and guarded control responsibilities:

  • the mobile API exposes Qobuz snapshot, queue, saved-queue, artwork, and

playback-control routes

  • supported controls include play, resume, pause, next, previous, seek, and

queue occurrence jump

  • the control adapter performs freshness/expectation checks and read-after-

write verification where possible

  • explicit renderer release/handoff is a separate lifecycle operation
  • Qobuz playback is not the same thing as browsing an authenticated Qobuz

library in the Sonuvi catalog

  • Qobuz queue occurrences and duplicates must be preserved

Relevant source includes pibuz-qobuz-control.mjs, qobuz-connect-control.mjs, qobuz-connect-release.mjs, and mobile.routes.mjs.

The existing docs/runbooks/28-qobuz-connect-now-playing.md contains useful provenance and release material, but parts of its Phase 1 description are now stale: it still describes the adapter as read-only and the earlier worktree as intentionally undeployed, while current main exposes the control routes and the tested release lifecycle. The historical Phase 1 language should be separated from the current implementation before that runbook is used as an agent instruction.

The Qobuz media-server experiment in docs/runbooks/29-upnp-queue-and-qobuz-media-server-poc.md must remain clearly separate from the working PiBuZ/Qobuz Connect path.

UPnP and renderer control

The current UPnP architecture includes:

  • discovery and renderer selection
  • browse/search and resource selection
  • renderer capability and transport inspection
  • preflight and session ownership
  • readiness polling before Play
  • stale-observation protection
  • duplicate-Play prevention after ambiguous SOAP responses
  • logical queue and occurrence control
  • mobile sanitization and authorization

The recent current-main change specifically waits for the expected renderer URI and readiness conditions before issuing Play, with a bounded fallback. DeepWiki page 7.9 captures the main control-point and queue protocol. Current main extends that description with the newer failure-sensitive readiness, stale-observation, and duplicate-Play behavior.

The current upnp-control-point.md is the right canonical home, but should cross-link the current session/readiness behavior and explicitly state which state belongs to the renderer, the Sonuvi control point, or MPD.

Audio diagnostics

The current GET /v1/mobile/audio-info contract is a sanitized mobile wrapper around the Track-Key-protected moOde/audio diagnostics path. It returns versioned, structured information and distinguishes measured values from configured values and unknown conversion. The mobile response does not expose filesystem paths, raw diagnostic commands, or private connection details.

DeepWiki page 9.7 covers the foundation of this behavior: the protected moOde/audio-info path, optional ALSA measurement, local source probing, and sanitized mobile diagnostics. It does not establish the current main revision's complete mobile wrapper, freshness fields, Qobuz/source handling, or exact privacy-redaction contract. This is therefore a reconciliation gap, not an absence of DeepWiki coverage.

Listening history

The current history implementation is broader than MPD polling:

  • source attribution is explicit
  • canonical/opaque identity resolution is validated
  • qualification and deduplication are server-owned
  • MPD observations remain a production input
  • mobile native playback reports progress/history through the mobile event

route

  • source-specific suppression prevents duplicate Qobuz/UPnP observations
  • Last.fm submission is asynchronous and does not define local history

The DeepWiki page titled Listening History and Scrobbling is a material documentation-generation defect: its own text says the supplied files do not establish local history or Last.fm behavior, while the sources it actually discusses are about-card.js, about.service.mjs, and apple-about.service.mjs. Page 7.9 does not fill that gap. The current history/scrobbling pipeline therefore remains absent from the reviewed DeepWiki content, and the mislabeled 6.6 page must not be treated as evidence for it.

External hardware and integrations

The current API registers and/or mediates several separately owned systems, including Seeburg, Multiphone/Mabel, Mills, Echo Link, moOde, AirPlay, UPnP, Qobuz/PiBuZ, Alexa, radio, podcasts, and YouTube. The Server is not the implementation owner of every external system. The integration boundary should identify for each system:

  • device/service owner
  • Server responsibility
  • direction of control and observation
  • credentials and trust boundary
  • history/scrobble attribution
  • failure/recovery behavior

DeepWiki's Alexa and moOde coverage is not enough to establish that matrix.

8. Server/iOS architectural boundary

DeepWiki page 7.9 covers part of the UPnP/Qobuz handoff boundary, but it does not settle the current standalone native iOS transition or the approved device-owned catalog target.

Current Server responsibilities

During the transition, the Server currently provides or mediates:

  • existing opaque mobile track identities and metadata resolution
  • Home queue/playback contracts
  • current mobile now-playing, next-up, Audio Info, and queue contracts
  • Qobuz Connect observation/control contracts
  • UPnP discovery/control contracts
  • local-source manifest availability
  • native playback-event ingestion for shared history
  • server-side qualification, deduplication, and Last.fm submission

Current native-client responsibilities

The native client owns its device UI, local playback mechanisms, and local storage/cache behavior. It uses scoped Server contracts for shared state, identity resolution, local-source availability, and history observation rather than receiving raw server internals.

Target architecture not yet implemented

The approved direction is an iOS-device-owned canonical Sonuvi Catalog with provider aggregation, persistent recording identity, attached-SSD observations/cache, and server-independent native playback. The target catalog authority, provider aggregation, canonical enrichment, and server-independent playback are not implemented in the current Server.

Documentation and future changes must label these as target behavior. They must not silently replace current opaque MobileTrack, Home queue, or mobile contract semantics.

  • POST /v1/mobile/playback/events
  • GET /v1/mobile/audio-info
  • current mobile now-playing/next-up and queue contracts
  • Qobuz Connect and mobile UPnP contracts where the native client uses them

The iOS client should remain on these explicit contracts. It should not reimplement Server-side playback arbitration or infer identity from artwork, titles, raw paths, or provider-specific URLs.

9. Risks revealed by the comparison

  1. Authority confusion: an MPD-only explanation can cause a future agent

to mutate MPD while Qobuz or UPnP owns playback.

  1. Queue confusion: treating Next Up, the MPD queue, a remote Qobuz queue,

and a UPnP logical queue as interchangeable can lose occurrence identity or issue controls to the wrong target.

  1. Authentication confusion: treating mobile bearer sessions as Track

Keys can produce contract or security errors.

  1. Documentation drift: stale Qobuz runbook statements currently conflict

with current control code and can lead to an unnecessary read-only design.

  1. History duplication: external-source and MPD observations must retain

explicit suppression/qualification rules.

  1. Diagnostics overclaiming: configured output must not be reported as

measured hardware output.

  1. iOS future-state leakage: target device-owned catalog behavior must not

be presented as current implementation.

  1. DeepWiki revision skew: a derived page can appear comprehensive while

predating a large feature set; the analyzed revision must always be recorded beside conclusions.

  1. Operational mismatch: installer documentation alone does not prove the

live service lifecycle, deployment helper, restart behavior, or recovery state.

10. Highest-priority recommendations

  1. Treat DeepWiki as a useful legacy orientation and independent terminology

review, not as an architectural source of truth.

  1. Correct the stale Qobuz runbook before using it as an AI/developer

instruction.

  1. Add one source/authority/queue/identity/auth/history matrix to the existing

architecture and playback pages.

  1. Make integrations.md and api-endpoint-catalog.md current indexes for the

newer Qobuz, UPnP, mobile, iOS, and external-hardware surfaces.

  1. Keep current and target iOS architecture explicitly separated.
  2. Preserve the canonical docs/wiki-source/ hierarchy and use focused pages

only where an existing hub cannot carry a contract safely.

  1. When using a future DeepWiki review, record its revision and compare it to

HEAD before accepting any architectural claim.

11. Remaining uncertainties

This audit intentionally stopped at source/documentation comparison. The following remain outside its evidence:

  • live behavior of every external renderer and hardware integration
  • current service state on the deployed Pi5
  • exact systemd/PM2 unit behavior where DeepWiki did not include the files
  • whether every current deployment host has the same configuration
  • provider-side Qobuz behavior outside the PiBuZ/Server contracts
  • native iOS implementation details beyond the Server-facing contract

Those questions require separate, explicitly authorized runtime or repository audits. They do not weaken the main conclusion: DeepWiki accurately captures the older Sonuvi foundation, but current architectural continuity depends on the source-backed boundaries documented above.
