# UPnP queue and Qobuz media-server proof of concept

This runbook records the Milestone 3 deployment and the preparation-only plan
for an isolated Qobuz UPnP MediaServer experiment. It does not authorize a
Qobuz login, Docker installation, image pull, container start, or new playback
mutation.

> **Status:** historical proof-of-concept and deployment record. It is not the
> current Qobuz Connect playback path. Current working Connect behavior uses
> the enhanced PiBuZ receiver and the guarded
> `/v1/mobile/qobuz-connect/*` contracts; current account/session status is
> documented by the Server's Qobuz account routes. The Docker/media-server
> restrictions and no-execution statements below remain in force for this
> historical experiment.

## 1. Current result

### Sonuvi queue

The deployed Sonuvi queue is a bounded, in-memory logical queue above the
existing UPnP AVTransport session manager.

- Queue item identity is generated by Sonuvi and is distinct from the
  ContentDirectory item ID.
- Items retain the media-server ID, item ID, opaque Browse/Search reference,
  metadata, artwork, duration, and resource format.
- Resource URIs are intentionally not persisted in queue state. The playback
  session re-resolves the current trusted resource immediately before loading
  it.
- Mutations require the current queue revision.
- Renderer ID, playback session ID, and session generation bind transport
  operations to the selected renderer/session.
- Queue advancement requires a confirmed playing-to-stopped transition at the
  reported track duration. A poll failure never advances the queue.
- The renderer's MPD queue is an implementation detail. Sonuvi does not
  snapshot or silently restore it.
- `upnp-sonuvi` shares the existing Qobuz/MPD ownership gate and MPD-history
  suppression; it does not create a second Last.fm/history event.
- State is memory-only so expiring signed resources cannot become durable
  queue identities. A service restart drops the queue and Sonuvi ownership
  without sending a renderer command.

Authenticated routes are documented in
[`docs/wiki-source/upnp-control-point.md`](../wiki-source/upnp-control-point.md).

## 2. Queue API contract

All routes use the existing Sonuvi Track Key. Mutation bodies contain opaque
item references and queue IDs only; they do not accept resource URLs or SOAP.

| Operation | Route | Required data |
| --- | --- | --- |
| Create | `POST /upnp/queues` | `rendererId`, optional ordered `itemRefs` |
| Read current | `GET /upnp/queue` | read-only current process-local queue |
| Read | `GET /upnp/queues/:queueId` | queue ID |
| Append | `POST /upnp/queues/:queueId/items` | `revision`, ordered `itemRefs` |
| Remove | `DELETE /upnp/queues/:queueId/items/:itemId` | `revision` |
| Clear | `POST /upnp/queues/:queueId/clear` | `revision` |
| Reorder | `POST /upnp/queues/:queueId/reorder` | `revision`, `itemId`, `toIndex` |
| Play | `POST /upnp/queues/:queueId/play` | `revision`, optional `itemId` or `index` |
| Pause/resume/stop | `POST /upnp/queues/:queueId/{pause,resume,stop}` | `revision` |
| Next/previous | `POST /upnp/queues/:queueId/{next,previous}` | `revision`, optional `autoplay` |

The desktop, tablet, and mobile Sonuvi shells expose these contracts through
the provider-neutral `Music Sources` page at `controller-upnp.html`. Browse
and search item artwork is served through
`GET /upnp/media-items/:selectionRef/artwork`; browser clients do not fetch
device-advertised LAN URLs directly. Loading the page performs no queue or
playback mutation.

The first queue implementation intentionally supports one active logical
queue per Sonuvi process. Queue revisions are optimistic concurrency control;
stale clients must reread the queue before retrying.

### Proposed isolated Compose file (not executed)

This is a template for a separate Linux or Mac-mini-hosted experiment. The
`QOBUZ_POC_LAN_IP` value must be the isolated host's LAN address; it is not a
Sonuvi or moOde address.

```yaml
services:
  qobuz-upnp:
    image: giof71/upmpdcli:master-2026-10-06-stable-full@sha256:6638389e24f58b960f33a4ec06cc7c3cf463040a26c8e8c41fc45f0b1fafc97d

      PGID: "${QOBUZ_POC_PGID:-1000}"
      UPNPIP: "${QOBUZ_POC_LAN_IP:?Set QOBUZ_POC_LAN_IP to the isolated host LAN address}"
      PORT_OFFSET: "6"
      RENDERER_MODE: "NONE"
      FRIENDLY_NAME: "Sonuvi Qobuz Library"
      QOBUZ_ENABLE: "yes"
      QOBUZ_TITLE: "Qobuz"
      QOBUZ_FORMAT_ID: "27"
      QOBUZ_RENUM_TRACKS: "1"
      PLG_PROXY_METHOD: "redirect"
      LOG_ENABLE: "yes"
      UPNP_LOG_ENABLE: "yes"
    volumes:
      - ./cache:/cache
      - ./log:/log
    cap_drop:
      - ALL
    security_opt:
      - no-new-privileges:true
    tmpfs:
      - /tmp:size=64m,mode=1777
    mem_limit: 512m
    cpus: "1.0"
    pids_limit: 256
    logging:
      driver: json-file
      options:
        max-size: 10m
        max-file: "2"
    labels:
      com.centurylinklabs.watchtower.enable: "false"
    restart: unless-stopped
```

The upstream startup script derives these ports from `PORT_OFFSET=6`:

- UPnP HTTP/device port: `49152 + 6 = 49158`;
- plugin micro-HTTP/OAuth callback port: `49149 - 6 = 49143`.

Host networking is required by the documented SSDP/multicast model. It also
means the container's UPnP device and HTTP resources are exposed on the
isolated host's LAN interfaces. The host firewall must allow only the trusted
LAN and the chosen ports; do not expose them through a public reverse proxy or
internet-facing firewall rule. Confirm both ports are unused before startup.
`RENDERER_MODE=NONE` prevents a second OpenHome/UPnP renderer; the compose
file deliberately has no `devices`, `privileged`, `MPD_HOST`, or ALSA mounts.

`/cache` is required for runtime state and the Qobuz plugin's
`/cache/qobuz/config` file. That file contains the Qobuz `user_id` and
`user_auth_token` after authentication. Protect the host directory with
restrictive ownership/permissions and never commit it. `/log` is optional but
bounded here to make credential-redaction and resource review easier.

The resource limits are starting safeguards, not measurements. No container
was run during this audit. Measure RSS, CPU, cache growth, and log growth in
the isolated trial before deciding whether the limits need adjustment.

## 4. Qobuz authentication and authorization

The current upstream utility is:

```text
/usr/share/upmpdcli/cdplugins/qobuz/qobuz-init-oauth.py
```

Its flow is:

1. Read the generated upmpdcli plugin HTTP host/port.
2. Instantiate `Bundle`, which fetches `https://play.qobuz.com/login` and its
   JavaScript bundle.
3. Extract the bundle's `app_id` and private key material.
4. Print a Qobuz browser URL using `ext_app_id` and a local or LAN redirect to
   `/qobuz/oauth/`.
5. The browser login returns an OAuth authorization code to the plugin's HTTP
   endpoint.
6. The plugin exchanges the code at `/oauth/callback`, calls `/user/login`,
   and writes `user_auth_token` and `user_id` to the Qobuz cache config.
7. Later plugin starts read those values, call `/user/login`, and replace the
   stored token when Qobuz returns a new one.

The flow does **not** collect or store the Qobuz password. It does, however,
reuse application material extracted from the Qobuz web bundle, uses private
Qobuz API endpoints, and has no documented token-expiry/refresh or revocation
workflow in the inspected source. Logout is not exposed as a ContentDirectory
operation; removing the cache file would remove the local copy but is not the
same as Qobuz-side revocation.

This is technically OAuth-shaped but not established as an authorized
third-party developer integration. Earlier policy review also found Qobuz's
current Help Center statement that only Qobuz apps can control devices via
Qobuz Connect, and Qobuz terms restricting service use and reverse
engineering. Those findings do not prove that a separately approved catalog
integration is forbidden, but they do block treating this plugin as approved.
No Qobuz account was authenticated during this work.

**Gate:** obtain written Qobuz authorization or official developer/OAuth
documentation before pulling the image or running `qobuz-init-oauth.py`.
Keep this media-server path separate from the working Qobuz Connect/Pibuz
path; do not reuse Pibuz tokens or route queue commands through Pibuz.

## 5. Qobuz ContentDirectory expectations

The inspected Qobuz plugin exposes a read-oriented ContentDirectory with:

- Discover Catalog, genres, featured/new releases, editorial playlists,
  artists, albums, and tracks;
- account favorites (albums, tracks, artists, playlists) after login;
- user playlist listing and playlist track browsing after login;
- server-side search for artists, albums, playlists, and tracks;
- Qobuz IDs carried through the plugin's `0$qobuz$` object-ID namespace;
- artwork, title, artist, album, track number, duration, streamability, and
  optional format metadata; and
- playable Qobuz resources obtained through the plugin's track URI handler.

The current plugin source contains read calls for favorites and playlists but
no ContentDirectory operations for adding/removing favorites or creating,
editing, or deleting playlists. Treat it as read-only for this POC. The media
server returns resource URLs that may be signed/short-lived; Sonuvi's queue
must resolve them at play time and never make them durable identities.

`RENDERER_MODE=NONE` means the container is a media server, not a control
point. The expected control path is:

```text
Qobuz account/API
        |
        v
upmpdcli Qobuz ContentDirectory (SSDP + Browse/Search)
        |
        v
Sonuvi queue + trusted AVTransport control point
        |
        v
moOde UPnP renderer -> MPD -> ALSA -> CAVALLI DAC
```

The container does not control moOde by itself. Sonuvi must remain the UPnP
control point, and the existing renderer ownership/Qobuz Connect gates apply.

## 9. Sonuvi Qobuz Account integration (Phase 1, 2026-10-13)

Phase 1 is implemented on Sonuvi only. It adds safe status reporting and
bounded unauthenticated-browse handling; it does **not** authenticate Qobuz
or invoke the installed OAuth helper.

### Implemented Phase 1 contract

The authenticated, read-only endpoint is:

```text
GET /config/qobuz/account/status
```

It uses the existing Sonuvi Track Key and returns only:

- `state`: `not_connected` or `connection_unavailable` in this phase;
- `reason`: a user-facing, sanitized explanation;
- `checkedAt`;
- safe MediaServer discovery facts (`id`, UDN, friendly name, and whether
  ContentDirectory/root browse were observed); and
- authentication state, which remains `not_verified` or `unknown`.

The endpoint probes discovered MediaServer roots and recognizes the Qobuz
provider only when a root item has the provider namespace `0$qobuz$`. An
advertised Qobuz container is not treated as a connected account. No Qobuz
password, token, application material, authorization code, cache path, or
signed resource URL is returned or read.

The `config.html` Qobuz Account card shows the current status and a disabled
`Connect Qobuz` action. It deliberately has no username/password fields. The
future connected, expired, pending, and disconnect states remain design-only
until an approved authorization mechanism exists.

When a browse or search request under the Qobuz object namespace times out,
the UPnP API returns `424 QOBUZ_AUTH_REQUIRED` with a sanitized reason. Only
that provider namespace is classified this way; generic ContentDirectory
timeouts remain generic `UPNP_TIMEOUT` failures. The Music Sources controller
also has a nine-second client bound and clears the loading state with a link
back to the Qobuz Account card.

### User experience

The deployed **Qobuz Account** card is under the existing Music Services
cards in `config.html`. It does not add username or password fields.

The card should expose these states:

- **Not connected** — Qobuz MediaServer may be advertised, but catalog
  browsing is unavailable until an account is connected.
- **Authorization pending** — show a short-lived `Connect Qobuz` action,
  authorization URL, expiry, and cancel action. Open the Qobuz page in a new
  browser tab or window; do not embed the login page.
- **Connected** — show only a safely available account label or masked
  identity, connection time, and a `Disconnect` action. Never display a token,
  application secret, authorization code, or cache path in the browser.
- **Error** — show a sanitized reason and a retry action; keep raw helper
  output server-side.

After successful connection, the UI should refresh Music Sources and show
Qobuz as an ordinary provider-neutral UPnP MediaServer. It must not start
playback or modify either the MPD Live Queue or the Sonuvi UPnP queue.

### Callback and control boundary

The installed helper is not a Sonuvi callback server. It prints a Qobuz URL
whose redirect targets moOde's upmpdcli plugin endpoint:

```text
browser -> Qobuz authorization -> moOde:49149/qobuz/oauth/ -> upmpdcli cache
```

Therefore Sonuvi cannot safely implement Connect Qobuz by merely redirecting
the browser to a public Sonuvi endpoint. A future implementation needs a
narrow, server-side moOde adapter that can:

1. start the helper on moOde through a fixed, audited operation;
2. return only a short-lived authorization URL and attempt ID;
3. monitor process completion and cache metadata without reading token values;
4. report sanitized status back to Sonuvi; and
5. remove the local authorization cache for Disconnect.

The adapter may be a moOde-supported service endpoint or a root-owned,
forced-command wrapper invoked only by the Sonuvi backend. It must not expose
arbitrary SSH, shell, SOAP, or port-49149 proxying to browser clients. The
existing callback endpoint must remain LAN-restricted and must not be
published through Caddy or the public Sonuvi site.

### Future authenticated Sonuvi endpoints

The status endpoint above is the only implemented account route. These
additional names remain illustrative and require a separate API/security
review before implementation:

```text
GET  /config/qobuz/account
POST /config/qobuz/account/connect
GET  /config/qobuz/account/connect/:attemptId
POST /config/qobuz/account/connect/:attemptId/cancel
POST /config/qobuz/account/disconnect
```

The responses may contain `state`, `attemptId`, `expiresAt`, a sanitized
`authorizationUrl`, `accountLabel`, and `lastError`. They must never contain
`user_auth_token`, application secrets, private keys, authorization codes,
Qobuz passwords, or raw helper logs. Every request uses Sonuvi's existing
Track Key/authentication model and CSRF protections where applicable.

The backend-to-moOde adapter should have an even smaller internal contract:

```text
start -> { attemptId, authorizationUrl, expiresAt }
status -> { state, accountLabel?, lastError? }
cancel -> { state }
disconnect -> { state }
```

### Token and secret storage

- Qobuz application material and account tokens remain only on moOde in the
  upmpdcli Qobuz cache, currently `/var/cache/upmpdcli/qobuz/config`.
- The cache directory and file must be owned by the dedicated service account
  with restrictive permissions; the exact token file contents must never be
  read into Sonuvi, browser storage, URLs, analytics, or logs.
- Sonuvi stores only connection state, an attempt ID, expiry, and optionally a
  provider-supplied non-sensitive account label.
- Disconnect removes the local cache through the moOde adapter. Local deletion
  is not equivalent to Qobuz-side revocation; an official revocation flow is
  required if Qobuz provides one.
- The helper's current source contains sensitive-value logging paths. Any
  future wrapper must redact or disable those logs before production use.

### Authorization prerequisites

Before implementing this UI or invoking the helper, obtain written Qobuz
authorization or official developer/OAuth documentation covering:

- use of application material derived from the Qobuz web bundle;
- the `/oauth/callback` and `/user/login` API flow;
- token storage, renewal, and revocation;
- LAN callback exposure; and
- streaming/catalog use by a third-party control point.

Do not reuse Pibuz credentials, add Qobuz credentials to Sonuvi config, or
assume that a technically successful OAuth exchange is an authorized
integration.

## 10. Installed-plugin security hardening (2026-10-13)

Before any future authentication test, the installed moOde Qobuz plugin was
hardened without contacting Qobuz or changing its authentication protocol.
The deployed changes are:

- `qobuz-app.py` no longer logs the complete callback request or raw
  authorization code; malformed/missing callbacks return a fixed failure page.
- `session.py` no longer logs the authorization code and returns success only
  when the exchange supplies both a user ID and a token before either value is
  written.
- `api/raw.py` no longer includes the token in its debug message.
- `/var/cache/upmpdcli/qobuz` is mode `0700` and the tracked systemd drop-in
  `ops/moode-overrides/etc/systemd/system/upmpdcli.service.d/10-qobuz-session-permissions.conf`
  sets `UMask=0077`, so a newly created cache file is private by default.

The reproducible source patch is tracked at
`ops/moode-overrides/upmpdcli-qobuz-oauth.patch`. The offline/live regression
harness is `ops/moode-overrides/test-upmpdcli-qobuz-oauth-hardening.py`; it
checks Python syntax, absence of raw request/code/token logging, truthful
success/failure callback responses, incomplete exchange rejection, and cache
directory/file plus service-umask metadata without reading cache contents.

The exact pre-patch files and hashes are preserved on moOde at:

```text
/var/backups/sonuvi-qobuz-oauth-plugin-20261013T093029Z/
```

After a package upgrade, record the new package version and hashes and back up
the exact installed files again. Apply the tracked patch only when its context
matches the installed source; do not force it across an upstream change. Run
the regression harness and restart only `upmpdcli` after a successful patch.
If the patch does not apply cleanly, stop for source review.

Rollback restores `qobuz-app.py`, `session.py`, and `api/raw.py` from the
timestamped backup, removes only the local plugin patch, reloads systemd, and
restarts `upmpdcli`. Keep the restrictive cache permissions unless separately
authorized to undo that hardening; never print or read the cache contents.

This patch does not resolve the separate Qobuz authorization/policy question.
No Qobuz login, application-material extraction, token access, catalog browse,
or playback was performed during the hardening work.
